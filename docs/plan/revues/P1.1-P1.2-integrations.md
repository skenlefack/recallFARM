## BLOQUANT

### B1 — USSD : la relance d'un saut rejoue l'action (mortalite comptee deux fois), en mode `last` et sous concurrence
- **Fichiers** : apps/api/src/connectors/ussd.ts:85-90 ; apps/api/src/notifications/ussd-session.service.ts:74-84 ; apps/api/src/notifications/inbound.service.ts:127 (`mortality: (existing?.mortality ?? 0) + n`).
- **Probleme** : la detection « relance identique » (`kind: 'repeat'`) n'existe qu'en mode `cumulative`. En mode `last`, tout saut apres un ecran de fin est re-evalue avec la saisie ajoutee. De plus `hop` lit l'etat, execute l'action puis ecrit l'etat sans verrou : deux sauts concurrents (relance de l'agregateur apres son delai, frequent en 2G) lisent le meme etat et executent tous deux l'action, dans les deux modes. La doc du service affirme pourtant « an action is never run twice ».
- **Scenario (sonde executee)** : etat `{inputs:['3','1','5'], raw:'5', end:true}` ; l'agregateur relance `text='5'` ; `readHop` renvoie `evaluate` avec `inputs ['3','1','5','5']` ; `ussdScreen` relit `parts[2]='5'` ; `journal.save` ajoute encore 5 morts (10 au lieu de 5). La mortalite declenche des alertes : fausses alertes sanitaires, donnees de surveillance faussees. Meme effet en `cumulative` si deux requetes `3*2*4` arrivent ensemble.
- **Correction** : (1) en mode `last`, si `state.end` et la derniere page est affichee, renvoyer `repeat` (l'ecran de fin) au lieu d'evaluer : un saut apres fin ne relance jamais l'action ; (2) verrou par cle de session (`kv.withLock` ou `SELECT ... FOR UPDATE` sur `ussd_sessions`) autour de load, action, save ; la requete perdante renvoie l'ecran memorise ; (3) action idempotente par session (cle d'operation `ussd:<session>:<etape>` memorisee avant execution). Tests : e2e mode `last` « relance de l'ecran de fin : mortalite inchangee » et deux sauts identiques en `Promise.all`.

## MAJEUR

### M1 — L'interrogation de statut ne traite pas le cas pour lequel elle est faite (paiement sans `provider_ref`)
- **Fichiers** : apps/api/src/billing/payment.providers.ts:127 (`provider_ref: payment.provider_ref ?? ''`) et :148-153 ; infra/providers/providers.example.json:61 (`/payments/{{provider_ref}}`) ; apps/api/src/billing/payment-ops.service.ts:307.
- **Scenario** : initiation en timeout (cas B2 de la revue precedente) : paiement `en_attente` sans `provider_ref`. Le poller appelle `GET /payments/` (variable vide) : selon l'agregateur, 404, 405, ou la **liste** (200) lue comme statut `inconnu`. Apres 6 essais le paiement passe `a_verifier` alors que l'eleveur a ete debite ; rien n'est confirme automatiquement. Meme probleme dans le rapprochement par statut (et une seule erreur interrompt tout le connecteur, cf. m3). Aucun test ne couvre « timeout a l'initiation, puis statut, puis confirme ».
- **Correction** : ne pas appeler `status` quand le gabarit utilise `{{provider_ref}}` et que la valeur est vide (retourner `null` avec la raison `sans_reference`) ; permettre une requete de statut par notre reference (`payment_id`) dans le descripteur et la documenter comme recommandee ; e2e : 503 a l'initiation, puis statut par reference, puis `confirme`.

### M2 — Anti-rejeu HMAC : la signature est consommee avant traitement, une relance legitime est refusee (401)
- **Fichiers** : apps/api/src/connectors/connectors.controller.ts:70 ; apps/api/test/connectors.e2e-spec.ts:407-413 (le test fige ce comportement).
- **Scenario** : webhook de paiement `SUCCESS` signe ; `applyResult` echoue (coupure PostgreSQL, verrou, deploiement) : 500. L'agregateur relance le meme corps avec la meme signature (cas usuel) ; `setNx` est deja pose : 401 a chaque essai. La confirmation est perdue jusqu'au poller, et definitivement si le connecteur n'a pas de requete de statut (`a_verifier`). Certains agregateurs desactivent l'URL apres une serie de 401. Meme effet sur un saut USSD signe relance apres timeout : 401 au lieu de l'ecran.
- **Correction** : poser la cle de rejeu apres un traitement reussi (ou la supprimer en cas d'erreur) ; pour un rejeu d'une requete deja traitee, renvoyer l'accuse habituel (200 `ack`) sans retraiter (paiement et DLR sont idempotents) ; garder le 401 pour une signature hors fenetre. Sans Redis, `KvService` en memoire n'est pas partage entre instances : le documenter ou utiliser une table.

### M3 — Remboursement : double remboursement possible et etat `remboursement_en_cours` sans issue
- **Fichiers** : apps/api/src/billing/payment-ops.service.ts:204-237 ; apps/api/src/connectors/connector.types.ts:171 ; apps/api/src/connectors/connector.validation.ts (`checkPayment`, partie `refund`) ; apps/api/src/billing/payment.providers.ts:162.
- **Scenarios** :
  1. Deux administrateurs (ou un double clic) lancent `/refund` en meme temps : la 1re transaction passe `remboursement_en_cours` ; la 2e obtient ensuite le verrou, voit `remboursement_en_cours` (statut accepte) et rappelle l'agregateur. Le seul garde-fou est `refund_id`, mais la validation n'exige pas que le gabarit `refund` utilise `{{refund_id}}`, et beaucoup d'API mobile money n'ont pas de cle d'idempotence sur les remboursements : deux remboursements de 2500 XAF.
  2. Reponse `en_attente` ou issue inconnue : aucun webhook de remboursement, aucune interrogation, et le rapprochement assimile `remboursement_en_cours` a `confirme`. Le seul moyen d'en sortir est de relancer `/refund`, qui renvoie une demande de remboursement (meme risque qu'en 1).
  3. Une reponse 409 « deja rembourse » a une relance est classee refus definitif : retour a `confirme` alors que l'argent est rendu, et un nouvel essai devient possible.
  4. Sans `result.status` dans le descripteur, tout 2xx vaut `rembourse` (payment.providers.ts:162) : un 202 « accepte, en file » est enregistre comme rembourse.
- **Correction** : (a) rejeter a la validation un `payment.refund` dont l'URL, les en-tetes ou le corps ne contiennent pas `{{refund_id}}` ; (b) dans la transaction, refuser un nouvel appel tant que `raw.refund.status` vaut `en_cours`/`en_attente` depuis moins de N minutes (409 `PAY-REFUND-IN-PROGRESS`) ; (c) ajouter une requete de statut du remboursement interrogee par le poller pour `remboursement_en_cours` (et/ou un webhook de remboursement) ; (d) permettre de declarer un code « deja fait » ; 202 vaut `en_attente` par defaut. Test : deux `/refund` en `Promise.all`, un seul appel agregateur.

### M4 — Preuves DoD incompletes sur le code d'argent
- **Fichiers** : apps/api/src/billing/payment-ops.service.ts (21 % des lignes en unitaire), apps/api/src/billing/admin-payments.controller.ts (0 %).
- **Probleme** : le code le plus sensible n'est prouve que par l'e2e, sans chiffre fusionne (DoD 2 : >= 80 % du code nouveau). Manquent : remboursement concurrent (M3), relance USSD en mode `last` (B1), timeout a l'initiation puis statut (M1), relance d'un webhook apres 500 (M2), poller qui chevauche (m1), rapprochement avec une erreur sur un seul paiement (m3). Le test e2e du rapprochement modifie la spec du registre en place (`delete spec.list`) : fragile si l'ordre des tests change.
- **Correction** : ajouter ces tests ; fournir la couverture fusionnee unitaire + e2e dans le rapport.

## MINEUR

- **m1** apps/api/src/billing/payments.scheduler.ts:26 et payment-ops.service.ts:83-100 — verrou de 55 s mais jusqu'a 100 interrogations sequentielles (timeout connecteur, doublees par le rejeu OAuth2) : au-dela, le cron suivant (meme instance ou autre) reprend les memes paiements, `next_at` n'etant ecrit qu'apres l'appel. Doubles requetes, risque de quota chez l'agregateur. Reclamer les lignes avant l'appel (`FOR UPDATE SKIP LOCKED` + ecriture de `next_at`), ou borner la duree du lot au TTL du verrou.
- **m2** apps/api/src/billing/billing.service.ts:128 — sans `id` ni `Idempotency-Key`, rien ne change : tant que web et mobile n'envoient pas l'id (requests.md, Ouvert), le double appui donne toujours deux debits. Un nouveau checkout (nouvel id) alors qu'un paiement de la meme formule est `en_attente`/`a_verifier` est accepte : deux invites, deux debits, abonnement prolonge deux fois. Suggestion : 409 `PAY-OPEN` avec le `payment_id` existant. Si `id` et `Idempotency-Key` sont fournis ensemble, la cle est ignoree en silence : refuser (422) ou verifier la coherence.

M1) classe tout le connecteur `non_verifies` ; le rapport etant stocke, `reconcileIfDue` ne le refait jamais (`hasReport`). - **m4** apps/api/src/billing/payment-ops.service.ts:270-291 — `totals` filtre par `created_at`, `confirmes_sans_abonnement` par `paid_at` ; le mode statut ne voit pas un paiement cree la veille et confirme le jour. Un paiement `rembourse` dont l'abonnement reste actif (Q-INT-01) n'est signale nulle part : l'ajouter au rapport. Le rattrapage ne couvre que la veille (« catches up after downtime » est trop large).
- **m5** apps/api/src/billing/billing.service.ts:200-206 — `settle` ne s'applique qu'a `initie` : si le webhook arrive avant la reponse HTTP de l'initiation, `provider_ref`, `ussd_push` et `redirect_url` sont perdus (la relance renvoie `provider_ref: null`, le rapprochement par reference echoue). - **m7** apps/api/src/billing/payment-ops.service.ts:240-241 — toute `TypeError` est classee « reseau » : un bogue de programmation laisse le paiement `remboursement_en_cours` au lieu de remonter. Tester `fetch failed` ou `e.cause`.

Renseigner `provider` a la migration quand il est connu, ou accepter `provider IS NULL` pendant une fenetre de transition ; noter dans le runbook qu'un down/up perd la colonne.
- **m9** apps/api/src/connectors/ussd.ts:8 et :24, apps/api/src/notifications/inbound.service.ts:88-137 — `max_chars` par connecteur (160 en dur par defaut) et non par pack pays comme demande dans la revue precedente ; la limite compte des unites UTF-16, or les textes contiennent l'apostrophe typographique U+2019 (hors GSM-7) : l'ecran part en UCS-2, ou beaucoup de reseaux limitent l'USSD bien sous 160 (environ 90). Utiliser l'apostrophe droite dans les textes USSD ou compter selon l'encodage (`smsSegments`). Textes du menu et « Suite » en francais dans le code sans cle i18n (Q-INT-06 ouverte).

- **m12** apps/api/openapi.json — les reponses (`replayed`, `checked`, `outcome`, `refund`, rapport de rapprochement) ne sont pas decrites (pas de DTO de reponse) : pas de schema pour les clients web et mobile.
